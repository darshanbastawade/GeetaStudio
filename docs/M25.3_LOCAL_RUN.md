## Selected resources and evidence

`ops/release-baseline.json` version 2 retains the prior hosting/SLO/recovery notes. Each selected feature needs 1–20 exact targets: `key`, `tenantId`, `universeId`, `resourceId`, `evaluationRunId`. READ resource is the exact active Public collection and key; WATCH resource is an approved production; ManualExport resource is a reviewed M18 package whose production is also selected under WATCH in the same tenant/universe. Empty target arrays deliberately block the current proposal. Disabled features do not require their human/live qualifications. Enabling an unsupported capability blocks the pilot rather than silently exposing it.

The collector calls existing READ, WATCH, M18 and M12 typed ports against current state. It retains their rights, human approval, exact audience/content, media and source-withdrawal gates. WATCH requires its original current renderer binding and Publish eligibility even though automatic publishing stays disabled. M18 requires a Manual package review and ExportOnly account. A stored fixture cannot be upgraded by adding an operational receipt. No source, evaluation or media registry is copied or replaced.

Run the decision first to obtain code/policy/configuration/manifest hashes and each target's subject/content/provider fingerprints and current module references. Obtain genuine reviews and measured reports for that exact candidate. `ops/release-evidence.json` is an index of operational evidence not already owned by the module stores; currently it is empty. It is not a readiness switch. Each receipt has:

- `id`, `feature`, `targetKey`, `kind`, `mode`, `subjectFingerprint`;
- `issuedUtc`, `expiresUtc` (maximum 30 days), `reference`, `path`, `sha256`;
- optional `revoked` and `supersededBy`.

Store these operational JSON files as UTF-8 without a BOM. Each SHA256-bound local proof is a structured report with `kind`, `mode`, `subjectFingerprint`, `outcome` (`Passed`), `observedUtc`, `fixtureOnly` (`false`) and nonempty `evidenceReferences`. OwnerScope, SecurityPrivacy and Usability require Human mode. Hosting, Monitoring, Recovery, MatchingCI and ProviderSwitch require Measured mode. The report must reference the genuine underlying review/drill/provider or CI records. A non-applicable provider switch must have a genuine measured applicability report bound to the actual stored/local provider set; disabled payments need no payment switch. No owner/human/measured reports have been supplied or fabricated here.

Human reports also need a nonempty `human:` reviewer reference. A report marked Passed is insufficient: `measurements` must satisfy the policy's named bounds, available in `ReleaseRules.Metrics`. SecurityPrivacy requires reviewed boundaries and zero critical/high findings. Usability requires participants/completed tasks and zero critical task failures. Hosting requires at least four checks and zero TLS/isolation/retention/secret failures. Monitoring requires at least 300 seconds and a successful alert test. Recovery requires positive measured RTO <=300 seconds, RPO <=900 seconds, restored records, and zero lineage/acknowledged-operation/asset/rollback failures. MatchingCI requires nonzero expected offline/SQL counts equal to passed counts, with zero failures/skips/format/model/high-vulnerability findings. ProviderSwitch requires actual checked operations with zero contract/resource/duplicate/unknown failures. These are qualification observations, not a claim of 30-day availability; actual sustained SLO evidence remains separate. Fixture-based CI test cases are legitimate; a fabricated CI report is not qualification evidence.

Proofs are operator attestations under filesystem ACLs, not cryptographic proof that a person performed a review. Operators must verify the referenced reports, identities, permissions and current approval before indexing them. This tooling cannot independently certify human honesty, legal rights or vendor invoices. Fixture flags/references, wrong modes, changed hashes/bindings, missing files, invalid/future/expired windows, revoked/superseded or ambiguous receipts block qualification. Evidence paths cannot escape the configured operational root or traverse filesystem links. Retain superseded files/history separately; the current index must identify exactly one receipt per required gate. Source/content/provider/code/policy/configuration or manifest changes require re-evaluation and new matching reviews, never editing an old ready flag.
